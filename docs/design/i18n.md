# Centralized i18n for Local Operator — Phase 0 RFC

**Status:** accepted · **Branch:** `docs/i18n-rfc` · **Author:** architect
**Verified against:** `origin/main` @ `54edc012a4` (2026-10-09), Textual 8.2.8 / Rich 15.0.0
(`.venv`), Node 26.5.0, `tsc` from `local-operator-ui/node_modules`, pyright 1.1.414.
Every count below was re-derived with the command shown, on that revision. Probe log in
[§12](#12-appendix--probe-log).

This RFC answers one question: **where does language live, and what does every surface
read it from?** The operator's requirement is backend-owned language — a single source of
truth inferred from the OS, settable in `config.yml`, `/settings` (TUI) and the UI, read
by TUI, desktop UI, `lop exec`, the Python SDK, the relay web, the mobile app and
`local-operator-ui`. The design below is the smallest one that keeps that promise without
breaking the contracts this codebase has already paid for: the prompt prefix cache, the
`lop exec` machine tokens, and the existing capabilities negotiation.

---

## 0. Decisions at a glance

| # | Question | Decision (recommendation) |
|---|---|---|
| 1 | Ownership & delivery | Core owns the contract and the `wire.*` namespaces; each client owns its own namespaces. Hybrid delivery: **bundle a bootstrap set**, **fetch `wire.*` from the backend** behind capability `i18n` |
| 2 | Format & layout | `local_operator/i18n/catalogues/<locale>/<namespace>.json`, flat dotted keys, ICU MessageFormat subset; per-key context sidecar on `en` only; key = `<namespace>.<area>.<element>[.<state>]` |
| 3 | Runtime deps | **No new Python dependency** — an in-house subset runtime (~400 lines) + data tables generated from Node `Intl` at build time, committed. TS surfaces use `intl-messageformat` (~117 KB unpacked, measured) |
| 4 | Generated types | TS: one generated key map + a **two-overload `t()`** (proven to reject all four negative cases). Python: **per-key generated functions** (proven; the `@overload` shape is not usable at this scale) |
| 5 | Locale resolution | Config `language: auto` (new registry key, LIVE scope); `auto` = `LOP_LANG` → OS → `en`. Live switch via `ConfigWatcher` + capabilities/desktop state. No per-surface override except mobile/UI pre-connection and `LOP_LANG` |
| 6 | Backend strings | Envelope `{code, params, text}` — additive: `text` stays for old clients. English-parsing consumers migrate to codes **before** their strings are translated |
| 7 | Not translated | Agent output, model-facing prompts/markers/tool descriptions, dev logs, commands/flags/identifiers, `--json` keys, docs & marketing (v1) |
| 8 | RTL | Full mirroring on web/Electron/RN; **TUI keeps LTR layout with per-string bidi isolation and a documented degraded stance for `ur`** |
| 9 | Formatting | One formatter layer per runtime over `Intl` (TS) and generated data tables (Python); Latin digits for `hi`/`ur` in v1 (style-guide decision) |
| 10 | Work split | Mechanism PR first, then ~54–56 extraction slices total (core ≈32–34: `wire.*` 6–8, TUI ~22, CLI ~4; plus UI ~12, mobile ~6, relay ~4); one namespace per PR; ratchet baseline touched only for the PR's files |
| 11 | Pipeline | LLM translator + independent auditor, results in a machine-readable ledger that gates both the locale picker and release; waves of 2 locales: es+fr → ru+vi → hi+zh-CN → ur |
| 12 | Tests | Pin `en` in fixtures; assert keys or en text under the pinned locale; the ~1,300 English-pinned assertions across repos keep passing unchanged |

Operator-level open decisions are collected in [§11](#11-open-decisions).

### 1.2 The parts of the architecture the design must not break

1. **Prompt prefix cache.** `prompts_api.build_system_blocks` (`prompts_api.py:907`) returns
   4 blocks; block 0 (standing instructions, persona + operator instructions) starts a
   persisted prefix epoch when it changes, and the tail's replaceable sections are
   recovered by **scanning for literal marker strings** (`_TAIL_SECTION_MARKERS`,
   `prompts_api.py:1259`; `STATE_SECTION_HEADINGS:1287`; the `[session-state]` sentence at
   `:1065`). Prompt text therefore stays English and byte-stable (§2.7, §10 risk 2).
2. **`lop exec` machine contract.** Parsers depend on exact English tokens:
   the receipt `Background job {job_id}: {status}` (`exec_mode.py:803`) is parsed by
   `_JOB_LINE_RE` (`session/bulk_resume.py:87-94`) and `_SESSIONS_JOB_LINE_RE`
   (`tools/builtin.py:13882`), the split spelling established in
   `tests/e2e/test_exec_output_modes_e2e.py:216-217`; `exec failed: ` prefixes are asserted
   (`cli.py:14547`, `exec_mode.py:1133`).
   Tokens stay; only the prose around them may translate.
3. **Capabilities negotiation.** `features` in `GET /v1/capabilities` is a pure function
   (`server/features.py::feature_flags`) with a non-HTTP reader (the mobile daemon imports
   it). A key's presence is the whole negotiation (`docs/DESKTOP_API.md` "Capability keys").
4. **Settings registry contract.** A new config key must exist in `SETTINGS` with a real
   consumer-default constant and an entry in `tests/unit/test_settings_io.py::_consumer_defaults`
   (AGENTS.md "Adding a configuration key"). `display.time_format` (`settings_io.py:2045`,
   consumed at `wakes/display.py:42`) is the precedent for a display-only LIVE key.
5. **Existing English-parsing consumers** must be migrated before translation:
   `incidents.cause_from_reason` (`incidents.py:997`, recovers a cause token *by parsing
   the rendered sentence*), `settings_io.split_value_rejection` (`settings_io.py:833`,
   matches message tails), the UI's `provider-catalog.ts` / `desktop-api.ts` /
   `use-agents.ts`, the relay web's `humanizeError` (`mobile/web/src/components/pending-card.tsx:80`),
   and the exec receipt parsers above.

## 2. Architecture

### 2.1 Ownership and delivery (item 1)

**Decision: core owns the contract and the shared `wire.*` namespaces; clients own their
own namespaces; hybrid delivery — every client bundles a bootstrap set, and the backend
serves the `wire.*` set.**

- Core repo owns: the message-id scheme, the envelope (§2.6), locale resolution (§2.5),
  catalogue file format & key naming (§2.2), the generated-types pipeline (§2.4), the
  checker (§2.7), the glossary/style-guide templates, and the ledger schema (§6).
- `wire.*` namespaces (errors, settings labels/help, slash-command descriptions, notices,
  incidents, exec prose) are **owned by core and served by the backend**:
  `GET /v1/i18n/catalogues/{locale}/{namespace}` → the message map + `content_sha256`,
  `ETag: <sha256>`, `Cache-Control: no-cache`, public like `/v1/capabilities`. Gate:
  `features.i18n = 1`.
- Every client bundles **its own** namespaces plus a minimal bootstrap of `wire.*`
  strings needed pre-connection (mobile login/pairing before any backend; UI installer
  window before a backend exists).

Why not the alternatives:

- **Bundle everything per client** (rejected): three release cadences would each pin their
  copy of `wire.errors.*`, then drift from the backend's `code`s as backend messages change
  between client releases. The envelope exists precisely to stop clients re-bundling
  backend-originated strings; bundling them defeats it.
- **Serve everything** (rejected): mobile cannot render a login/pairing screen before a
  backend is reachable, and the Electron installer window runs before `lop` is installed.

Cost of the hybrid: two resolution sources to reconcile. The rule is small and testable:
**served catalogue wins for `wire.*` when connected and the capability is present; bundled
bootstrap is the fallback**; client-owned namespaces are never served. Version skew is
handled by the content hash — the client caches by hash and re-fetches on change.

Operationally: the route is cheap (static JSON, ETag revalidation), ships dark (en only)
in Phase 1, and no existing client changes behaviour when the capability is absent.

### 2.2 Catalogue layout, key naming, context sidecars (item 2)

```
local_operator/i18n/                     # SHIPPED (package data; precedent: prompts_md/, guides/, agent_seeds/)
  catalogues/en/<namespace>.json         # authored source
  catalogues/<locale>/<namespace>.json   # translated
  catalogues/en/<namespace>.context.json # en only: per-key role/tone/maxCells/notes
  data/plural_rules.json                 # generated (§2.3)
  data/formats.json                      # generated (§2.3)
local_operator/i18n/keys/<namespace>.py  # generated Python key functions (§2.4)
i18n/                                    # REPO artifacts, not shipped
  ledger.json  baseline.json  allowlist.toml
  style-guides/<locale>.md  glossary.md
```

Catalogues must ship in the wheel (the backend serves them from an installed package), and
the existing package-data mechanism (`pyproject.toml:224`, guarded by
`tests/unit/mobile/test_web_package_data.py`-style tests) is the well-trodden path. The
process artifacts (ledger, baseline, style guides) are repo-only.

**File shape:** one JSON object per file, flat dotted keys → ICU message strings:

```json
{
  "wire.errors.model_unavailable": "Model {model} is unavailable.",
  "tui.welcome.tip_resume": "{count, plural, one {# session} other {# sessions}} to resume"
}
```

**Namespace and key naming.** A **namespace** is the dotted prefix up to the file
boundary — the file is `catalogues/<locale>/<namespace>.json` (e.g. `wire.errors.json`,
`tui.splash.json`) — and it is the ownership unit (one owning repo/area, one file, one PR
slice). A namespace larger than the PR budget is subdivided into **child namespaces**
(`wire.errors.auth`, …), each a new file with its own owner (§5).

**Keys** are `<namespace>.<area>.<element>[.<state>]` — globally unique, repeating the
namespace prefix — all-lower `snake_case`, ASCII. Examples:
`wire.errors.model_unavailable`, `tui.settings.save_failed`,
`ui.chat.composer_placeholder`. Keys never contain interpolation; state suffixes are
explicit (`_empty`, `_error`).

**Context sidecar** (`en` only), keyed by message id, is part of the contract, because the
TUI's width budgets are real (42/43-cell `PERSIST_HINT`, 59-cell tip pool, ~55-col `/help`):

```json
{ "tui.settings.help.language": { "role": "help text", "tone": "plain", "maxCells": 43,
  "note": "one clause; wraps, never truncates" } }
```

### 2.3 Runtime and dependencies (item 3) — operator-level

**Python: no new dependency.** Implement an in-house runtime in `local_operator/i18n/`
that parses the ICU subset we allow: `{name}` interpolation, `{n, plural, ...}`,
`{n, select, ...}`, and a small set of number/date skeletons. Everything locale-specific
is **generated at build time by a dev-only Node script** (Node is already a dev/CI
dependency) that reads `Intl.PluralRules`/`Intl.NumberFormat`/`Intl.DateTimeFormat` and
writes committed tables: plural categories per locale, number separators and grouping
(incl. `hi`'s 3;2 Indian grouping), month/weekday names, and date/time patterns for the 8
locales. Correctness is anchored to the same `Intl` the TS surfaces use, plus golden
tests.

Alternative considered — **Babel**: correct for free, but the wheel is **10,196,845 bytes
(9.7 MiB)** on PyPI (measured), for the ~5% of it we need; the disk/RAM budget on this
fleet is explicitly scarce, and this repo already prefers generated data over weight
(`prompts_md`, `agent_seeds`). Cost of being wrong: subset-parser edge cases; mitigation
is a parity matrix run in dev that renders every message with both runtimes. **This is an
open decision for the operator (§11.5).**

**TS surfaces (UI, relay web, mobile): `intl-messageformat`** (`@12`, 117,556 bytes
unpacked, plus `@formatjs/icu-messageformat-parser` 250,012 bytes — measured) over native
`Intl.PluralRules`/`NumberFormat`. Hermes (RN 0.70+, mobile is 0.86) implements the
ECMA-402 subset this needs. Alternative — precompile catalogues to functions at build
time (formatjs CLI): no runtime dep, but a build step in three repos; revisit only if a
bundle budget bites.

**Python format layer** (`i18n/format.py`): numbers, currency, percents, dates, relative
time, durations, byte sizes — thin wrappers over the generated tables; it replaces
`wakes/display.py`'s hand AM/PM and the `' ago'` concatenations. No `locale` stdlib
formatting (process-global, Unix-only).

### 2.4 Generated types (item 4) — proven by spike

Both spikes ran on this host against the real toolchains (probe log §12).

**TypeScript — decision: one generated key map + a two-overload `t()`.**

```ts
export interface MessageParams { 'tui.welcome.tip_resume': { count: number }; … }
export type MessageKey = keyof MessageParams;
type WithParams = { [K in MessageKey]: MessageParams[K] extends undefined ? never : K }[MessageKey];
type WithoutParams = { [K in MessageKey]: MessageParams[K] extends undefined ? K : never }[MessageKey];
export function t<K extends WithParams>(key: K, params: MessageParams[K]): string;
export function t<K extends WithoutParams>(key: K): string;
```

Measured: 10,000 keys + 5,000 call sites, `tsc --strict` in **10.5 s**, and all four
negative cases rejected (bad key; bad param type; missing required params; params on a
no-params key) — the spike's four `@ts-expect-error` directives were all *used*, i.e. tsc
really does reject each. A cheaper-looking single conditional-tuple signature
(`...args: Params extends undefined ? [] : [p: Params]`) was tried first and **failed to
reject a missing params object**, so it is explicitly not the shape to generate.

**Python — decision: per-key generated functions per namespace. Do not generate `@overload`s.**

```python
# local_operator/i18n/keys/wire_errors.py  (generated)
def model_unavailable(*, model: str) -> Msg: return Msg("wire.errors.model_unavailable", {"model": model})
```

Measured with pyright 1.1.414: 10,000 generated functions across 40 modules + 5,000 call
sites typecheck in **3.5 s**, and pyright rejects a mistyped key
(`"kzz" is not a known attribute of module`), a bad kwarg type, and an unexpected
positional argument. The `@overload`-per-key shape (5000 overloads in one module) **did
not finish in 120 s** and was killed — it is not viable at catalogue scale.

Generation is a checked-in script (`scripts/i18n/generate.py`, driving a small
`scripts/i18n/emit.mjs` for the `Intl` data); CI regenerates and fails on drift. A
mistyped key therefore fails `tsc` and `pyright`, and a param-shaped mistake fails both —
which is the requirement.

### 2.5 Locale resolution and live switching (item 5)

New config key **`language`**: `auto | en | fr | es | zh-CN | ru | vi | ur | hi`,
default `auto`, registered in `SETTINGS` (new row under `appearance`-style LIVE scope;
consumer constant `DEFAULT_LANGUAGE = "auto"` next to the resolver, and an entry in
`_consumer_defaults()`). `lop config edit`/`config list` and `/settings` pick it up for
free.

Resolution (highest wins): explicit config tag → `LOP_LANG` env (tests, exec, overrides) →
OS → `en`. `auto` never resolves to an unaudited locale: the supported-locale filter checks
the ledger/shipped set (§6).

OS detection: **macOS** — read `AppleLanguages` from
`Library/Preferences/.GlobalPreferences.plist` with `plistlib` (stdlib; measured **1.8 ms**
vs **290 ms** for a `defaults read -g` subprocess — prefer the plist, keep the subprocess
as fallback when the file is absent). **Linux** — `LC_ALL` > `LC_MESSAGES` > `LANG`, then
`LANGUAGE` list. **Windows** — `GetUserPreferredUILanguages` (ctypes) with `locale.getlocale()`
fallback; documented, not yet measured on our CI. Mapping: strip region → language →
`en`; `zh*` → `zh-CN`; `zh-TW/Hant` unsupported in v1 (falls back to en).

**Live switch without restart:** `ConfigWatcher` (2 s stat poll, `config_watch.py:156/209`)
fans the change out; the resolved language is added to `GET /v1/capabilities` (a
`desktop`-state field beside the feature map) and clients re-read it (TUI at next paint;
UI on its existing poll/SSE). `lop exec` and the SDK resolve per call — each is a fresh
session, so there is nothing to push.

No per-surface override in v1, with exactly two documented exceptions: (a) mobile/UI
**before any backend is reachable** use the device locale; (b) `LOP_LANG` for tests and
`exec`.

### 2.6 The message envelope (item 6)

```json
{ "code": "wire.errors.model_unavailable", "params": {"model": "gpt-x"}, "text": "Model gpt-x is unavailable." }
```

`text` is always present (en, or the resolved locale when known) so **older clients keep
reading exactly what they read today**; `code`/`params` are additive. Adoption points:

- `NoticeEvent` gains optional `code`/`params` (`harness/types.py:2235` — the same additive
  shape as `headline`, which rode the event because re-parsing prose at the viewer is the
  fragile thing the field exists to avoid).
- `HTTPException(status, {code, params, text})` — FastAPI `detail` accepts JSON; the
  contract becomes `detail: str | {code, params, text}` and routes migrate in slices.
  Precedent exists: `desktop_sessions.py:1004` already refuses with `{code, message}`.
- `CRUDResponse.message` stays a string in v1; a later slice may add `message_code`.
- Wire frames (`{"op": "error", "message": …}`, 14 sites) gain `code`/`params` alongside
  `message`.

**Precondition work items** (must land before the related strings translate): migrate
`incidents.cause_from_reason`, `settings_io.split_value_rejection`, the three UI parsers,
the relay `humanizeError`, and the exec receipt consumers to read `code` first; then the
English text they used to parse is free to translate.

### 2.7 Enforcement (brief item 5)

- **Python AST ratchet** — `scripts/i18n/check.py`, run as a unit test and as a CI job:
  flags literals reaching `Text.append`/similar Textual text sinks, `SlashCommand`/
  `Setting` copy fields, `NoticeEvent`, `argparse` `help=`, `print`/`console.print`,
  `HTTPException` detail, `CRUDResponse(message=)`; allowlist + `# i18n: ignore <reason>`
  pragma; per-file baseline in `i18n/baseline.json` that may only stay equal or go down;
  **new files start at 0**. **Enforcement is scoped and ships ADVISORY in P1:** the
  baseline carries an `enforced` list of path prefixes; findings outside it print as
  `advisory:` lines and do not fail (a concurrent fleet must not go red before an
  extraction slice exists to give a string a key), while an extraction slice
  **activates its own area** by adding that area's prefix in its own PR; P5 flips the
  whole tree. Catalogue parity and generation drift stay blocking everywhere.
- **TS scanner** — a script on the TypeScript compiler API (both client repos already
  carry `tsc`), run in each repo's test/CI path (UI: `node:test` scripts + Biome stays
  separate; relay: the `mobile-web.yml` pnpm job; mobile: vitest/typecheck). Biome 1.9.4's
  GritQL `biome search` is not a substitute; analyzer plugins are a Biome 2.0 feature —
  do not depend on them for v1.
- **Catalogue parity** — every locale has every key, same placeholder set, plural
  categories valid for that locale (per the generated plural table). Runs in the same
  `i18n` CI job.
- **Scope-awareness** — locales/scripts are **live** (a new category in
  `scripts/ci_scope.py`, alongside today's inert `docs` and `web` rules at
  `ci_scope.py:132-140`), so Python jobs run when catalogues change; the four TS surfaces
  stay behind their existing path-gated workflows.
- **Allowlist document** — `i18n/allowlist.toml`, one entry per exemption with a required
  reason: `[["local_operator/cli.py", "argument placeholder, not prose"]]`. Categories:
  commands/flags/identifiers, dev logs, tool names, `--json` keys/event types, model-facing
  prompts, code snippets/paths.

### 2.8 Formatting and digits (item 9)

One formatting layer per runtime: TS wraps `Intl` (measured behaviour in §12 table:
`fr 1 234,5` with U+202F, `hi 12,34,567.5` Latin digits Indian grouping, `ur` Latin digits
+ `AM` suffix in dates, `zh-CN` "…年…月…日"), Python uses the generated tables. All
hand-rolled plurals (`tui` 85, UI 205, mobile 7) become ICU `plural` selections. **Digits:
Latin for `hi` and `ur` in v1** — Node `Intl` already returns Latin digits for both by
default (measured); native-digit output would require the `nu` extension and a style-guide
call per locale. That stays a per-locale style-guide entry, revisitable without code.

## 3. Per-surface plan

### 3.1 Core TUI / CLI
Helper `tr(Msg) -> Text/str` at render points; widgets keep layout, swap string sources.
`/settings` gets a `Language` row (ENUM over shipped locales + auto; unaudited locales are
not listed). Width-sensitive strings carry `maxCells`; the three pinned budgets get
per-locale tests. `/help`, `PERSIST_HINT` and the tip pool are re-measured after each
translation wave (evidence: rendered frames, per AGENTS.md "Visual validation").

### 3.2 Desktop UI
`src/i18n/` with generated `keys.gen.ts`, `t()`, locale from backend capabilities (falling
back to device locale pre-connection); `Intl` formatters centralised; main-process
menus/dialogs/notifications get a main-process catalogue (they cannot import renderer
code); `dir`/`lang` on `<html>`, logical CSS properties; directional glyphs mirrored. The
evidence manifest pins `src` → **any `src` change forces evidence re-capture**; plan for it
in the first extraction PR.

### 3.3 Relay web
Copy into `src/i18n/`, locale via the public capabilities route (falling back to
`Accept-Language` pre-auth? No — pre-auth uses the browser's `navigator.language`; the
login page is inline HTML in `daemon.py:7299` and the SPA shell is a `FileResponse`
(`daemon.py:4301`) — set `lang`/`dir` from JS on boot for the SPA, and from the resolved
locale for the login HTML). `I18nManager`-equivalent: `dir=rtl` + logical properties;
LTR islands for code/paths/terminal output.

### 3.4 Mobile
Copy into `src/i18n/` (the repo's `docs/architecture.md:308` already prescribes "keep copy
out of components in one catalogue"). Device locale pre-connection via Hermes `Intl`
(`Intl.DateTimeFormat().resolvedOptions().locale`) and `I18nManager` for RTL — **no
`expo-localization` in v1** precisely because it is a native-module change (new store
build, not OTA) and v1 keeps the JS-only path. Native strings (`NSMicrophoneUsageDescription`
at `app.config.ts:127`, Android channel name) translate only when a native build is cut
anyway; they ride `mobile.native` and are exempt from over-the-air expectations. Push text
is composed machine-side (ADR 0006), so push language is a **backend** decision and lands
when the backend is translated.

### 3.5 SDK / `lop exec` / machine surfaces
`lop exec` human prose translates; the machine tokens of §1.2 stay byte-stable (the parser
sites are listed as contract tests). The SDK (`local_operator/sdk.py`, on `origin/main`)
reads the config language; a per-call override is `LOP_LANG` only.

### 3.6 Docs site & marketing — out of scope for v1
(§11.6). The docs search tokenizer is English-only; translating docs is a different
pipeline (MDX, search index) and is not on the critical path for product language.

## 4. RTL and fonts — what a terminal can and cannot do (item 8)

Measured on this host (probe log §12):

- **Rich 15.0.0 / Textual 8.2.8 contain no bidi, no Arabic shaping, no RTL code** — a
  case-insensitive search for `bidi|rtl|arabic|shap(e|ing)` over both packages' Python
  matches nothing.
- A Rich console round-trip **preserves storage order byte-identically** — no reordering
  happens, so an Urdu string prints in logical order.
- Cell widths: FSI/PDI/RLM/LRM cost **0 cells** each (so per-string bidi isolation is
  width-free); Devanagari conjuncts measure "optimistically" (`क्षत्रिय` 8 code points → 5
  cells; `मैं` 3 → 1 — matching what terminals that shape would show, and also what a
  non-shaping terminal *mis*-places); ZWJ emoji 2 cells.

What terminals actually do (documented upstream, not measured here): **iTerm2** has had
bidi reordering + Arabic/Persian cursive joining **enabled by default since 3.7.0**
(changelog: "Right-to-left script support … enabled by default", Settings > General >
Experimental; the installed build here is 3.5.14, i.e. *older*). **kitty** has no
line-level bidi in the grid (the upstream `kitty-rtl` fork exists for exactly that gap).
**Ghostty** has an open bidi feature request. **Terminal.app** was not measured.

**Decision.** The TUI keeps LTR layout and ships `ur` as **best-effort/degraded**: each
translatable string is wrapped in FSI/PDI isolation (zero width, storage order preserved),
which renders correctly on bidi-capable terminals (iTerm2 3.7+) and remains legible-but-
unordered on the rest. The degraded stance is documented in the style guide and the
locale picker (a note on the `ur` row). Full mirroring is delivered where we own the
renderer: **desktop UI, relay web, mobile** — `dir=rtl`, logical CSS properties, mirrored
directional icons, LTR islands for code, paths, diffs and terminal output. An
interleaved-Urdu-plus-Latin-layout terminal is not achievable from inside Textual and is
not attempted.

**Fonts.** macOS ships the needed families (verified by `ls`): CJK (Hiragino Sans GB,
CJKB SymbolsFallback), Devanagari (DevanagariMT, ITFDevanagari, Kohinoor, SFIndia),
Arabic-script (**DecoTypeNastaleeqUrdu.ttc, NotoNastaliq.ttc**, GeezaPro, SFArabic). The
TUI inherits whatever the user's terminal uses — recommend documenting a font table in the
style guide (Nastaliq for Urdu, a Devanagari-capable font for Hindi). Web/Electron use the
system stack already (no `@font-face` today); mobile is **Figtree-only** and relies on
per-glyph system fallback — bundled subsets are an open budget decision (§11.4), and any
bundled font is a native-asset change (new build).

## 5. Work partitioning for Phase 1 (item 10)

**Ordering rule:** one mechanism PR (M0) in core, then the extraction fan-out. M0:
runtime package + generated types + `language` config key + resolver + `/v1/i18n` routes
+ `features.i18n` + checker skeleton + `en` catalogues for the `wire.*` set (populated by
the wire slices, which run right after M0). Nothing user-visible until a wave passes
audit (§6).

**Namespaces** (owning repo → namespaces → approximate site count from §1):

- core·served (`wire.*`): `wire.errors` (329 HTTP sites; subdivides into ~3 child
  namespaces by route area, each its own file/slice), `wire.settings` (201), `wire.slash`
  (49), `wire.notices` (29), `wire.incidents` (~300 sentence-map entries), `wire.exec`
  (receipts/help prose in `cli.py`/`exec_mode.py`).
- core·TUI (`tui.*`, ~22 slices): splash/welcome, status line, transcript, tool cards,
  session panel/sidebar/picker, asks, settings view, projects, analytics, usage, network,
  subagents, composer/editor, notifications, help/about, copy picker, projects renderer,
  bindings, `app.py` residue.
- core·CLI (`cli.*`, ~4 slices over the 664 `print(` sites and 249 `help="` sites; 237 of
  the `help="` sites fall in the first 3,000 lines, the parser-builder region).
- UI (`ui.*`, ~12): `ui.chat` (405 sites — split into 3–4 sub-slices by component group),
  projects, settings, browser, agents, schedules, hub, mesh, onboarding, console,
  providers/palette, `ui.shell` (main-process menus/dialogs/notifications).
- mobile (`mobile.*`, ~6): auth, home, session, settings, connection/deep-links, `mobile.native`.
- relay (`relay.*`, ~4): login, shell, session, asks/cards.

**Rules.** One namespace per PR; a PR owns its namespace file(s) plus its code file group;
target ≤250 message sites and ≤15 touched files per PR; the ratchet baseline is updated
only for the PR's own files (`scripts/i18n/check.py --update <paths>`) so baseline edits
rebase mechanically; keys are immutable once shipped — a rename is delete+add, which
invalidates ledger entries by `source_sha256` (by design).

**Collision rule.** A namespace names exactly one catalogue file and is owned by exactly
one repo and one slice; two slices never write the same file. Where a namespace exceeds
the PR budget it is subdivided into child namespaces (new files), each owned by its own
slice; the `wire.errors` route-area split is the first example. The only shared file is
`i18n/baseline.json`, and only through the per-file update command above.

**Count:** core ≈32–34 (`wire.*` 6–8 — `wire.errors` subdivides into ~3 child namespaces by
route area — plus `tui.*` ~22 and `cli.*` ~4) + UI ~12 + mobile ~6 + relay ~4 ≈
**54–56 independently mergeable slices** after M0 — designed so ≥8 sessions can work in
parallel without file overlap.

## 6. Translation and audit pipeline (item 11)

- **Agents:** translator profile `i18n-translator`, independent auditor `i18n-auditor`
  (both already exist harness-side, per the operator). One translator and one *different*
  auditor run per (locale, namespace), each recorded with agent+model.
- **Ledger** (`i18n/ledger.json`): per (locale, namespace):

```json
{ "locale": "fr", "namespace": "wire.errors",
  "source_sha256": "<sha256 of locales/en/wire.errors.json at translation time>",
  "translator": {"agent": "i18n-translator", "model": "…", "date": "…"},
  "auditor":    {"agent": "i18n-auditor",  "model": "…", "date": "…", "result": "passed", "findings": 0},
  "status": "passed", "note": "" }
```

- **Gate:** a locale is *shipped* iff every namespace in the ship set has `status: passed`
  and a **fresh** `source_sha256` (hash of the current `en` file). Stale hash ⇒
  automatically `stale` ⇒ not shipped ⇒ the picker omits it and `auto` will not resolve to
  it. Two consumers: the config/picker (which locales exist) and the release check (CI job
  in the same `i18n` workflow). Catalogues may ship stale content to a connected client
  only as en-fallback, never as a shipped locale.
- **Style guides:** `i18n/style-guides/<locale>.md` + shared `i18n/glossary.md`. Template
  fields: formality (tu/vous, Sie/du, 您/你), product-name policy (keep English: "Local
  Operator", "lop", tool names, `--flags`, identifiers; decide per locale for
  session/wake/agent/trace — default: translate common nouns, keep product-surface names),
  kept-English technical list, digits policy (§2.8), RTL note for `ur`, width rules.
- **Waves** (scarce RAM/disk, and each wave needs render/QA attention): **es+fr → ru+vi →
  hi+zh-CN → ur** (last, because it carries the RTL pass). Two locales per wave, one
  translator run + one auditor run per (locale, namespace), results committed as one
  ledger update per wave.
- **Release gate:** the shipped-locale set is computed from the ledger at packaging time
  and embedded in the wheel data (`data/shipped.json`), so an un-audited locale cannot
  leak into a release even if its files exist.

## 7. Test strategy for English-pinned assertions (item 12)

- **Pin `en` in fixtures**: TUI/unit tests run with `LOP_LANG=en` (documented alongside the

## 9. Rollout, kill switch, rollback

- **P0** approve this RFC + §11 decisions.
- **P1** core M0 mechanism + checker + `wire.*` extraction; `features.i18n` ships;
  catalogues en-only; no user-visible change. The ratchet ships **advisory**:
  findings outside the enforced scope (`local_operator/i18n/` + `scripts/i18n/` at
  first) report without failing; each extraction slice activates its own area.
- **P2** extraction fan-out across all repos (en-only; extraction should be
  byte-identical output, so visual reviews wait for translations).
- **P3** wave 1 (es+fr) translated, audited, ledger-passed → pickers gain locales; TUI/UI
  visual rounds; first `/settings` and UI language selectors go live.
- **P4** waves 2–3 (ru+vi, hi+zh-CN) + `ur` with the RTL pass.
- **P5** enforcement tightens: the enforced scope covers the whole tree (the
  advisory window closes), baseline frozen, allowlist pruned; new violations fail.
- **Kill switch:** force `language: en` (config) or `LOP_I18N=0` (env; runtime returns en,
  routes keep serving en catalogues). Clients treat unknown/absent locales and failed
  catalogue fetches as en-fallback; a stale ledger entry auto-hides a locale.
- **Rollback:** setting the kill switch is non-destructive and instant (next paint / next
  call). Reverting code follows normal PR revert; no data migration exists to undo.

## 10. Risks

1. **Widths** — translations expand; the three pinned budgets are the brittle part. Watch:
   `maxCells` compliance tests, rendered before/after frames per wave.
2. **Prompt cache** — any change inside prompt text invalidates prefixes. Guard: prompts
   stay English; the single "respond in <language>" line is appended to the HEAD block at
   session creation only (alongside `user_instructions`, which the codebase already treats
   as head-stable), never re-written mid-session; resumed sessions keep their persisted
   bytes.
3. **Ratchet churn** — a scanner with false positives gets allowlisted into uselessness;
   the allowlist requires reasons and is pruned at P5.
4. **Two-source reconciliation** — bundled vs served `wire.*`; one function resolves it,
   tested.
5. **Generated-data drift** (Python tables vs `Intl`) — parity matrix in dev; regeneration
   is CI-checked.
6. **Mobile native step** — if bundling fonts or adding `expo-localization` happens later,
   it forces a store build; v1 avoids both deliberately.

## 11. Open decisions

**Resolved 2026-10-09 (operator-approved): all six ⛳ items are adopted ON THEIR
RECOMMENDATIONS** — wire-vs-bundle hybrid (§2.1), mobile pre-connection device locale,
best-effort/degraded Urdu in the TUI, no bundled fonts, no new Python dependency, and
docs/marketing out of scope for v1. The architect-level items (7–9) ride as recorded.

Operator-level items (⛳) each carry a **recommendation**, an alternative and the cost of
being wrong; architect-level items (7–9) are recorded decisions, listed for visibility.

1. ⛳ **Wire-vs-bundle split.** *Recommend:* hybrid (§2.1) — bundle bootstrap, serve
   `wire.*`. *Alternative:* bundle everything per client (simpler runtime, guaranteed
   drift from backend codes and three copies to update). *Cost of wrong:* two resolution
   paths to reconcile; if rejected towards bundling, the envelope's value shrinks to
   "clients that do fetch".
2. ⛳ **Mobile pre-connection device locale.** *Recommend:* yes — device locale for
   pre-connection surfaces only, backend language from connect onward. *Alternative:*
   en until connected (simplest, visibly wrong for a fr/es user's first screen). *Cost of
   wrong:* one extra resolution path on mobile; a device set to an unsupported locale
   falls back to en anyway.
3. ⛳ **Urdu in TUI.** *Recommend:* ship best-effort/degraded (§4) with FSI/PDI isolation
   and a picker note; correct on iTerm2 3.7+, unordered-but-legible elsewhere.
   *Alternative:* hold `ur` in the TUI until a future bidi-capable approach (the codebase
   cannot reorder text; a wrapper would only help if terminals render it). *Cost of
   wrong:* Urdu TUI users on non-bidi terminals see scrambled ordering; holding `ur`
   costs the locale its whole terminal audience.
4. ⛳ **Bundle/binary-size budget for fonts and catalogues.** *Recommend:* v1 ships **no
   bundled fonts** (system fallback everywhere; mobile stays OTA-shippable), catalogues
   are JSON (tens of KB per locale) — no budget pressure. *Alternative:* bundle CJK/
   Nastaliq subsets for mobile (~10–30 MB) + native build. *Cost of wrong:* poorer glyph
   rendering on bare systems; bundling later is additive.
5. ⛳ **New Python dependency.** *Recommend:* none — in-house subset + generated `Intl`
   tables (§2.3). *Alternative:* Babel (9.7 MiB wheel, correct ICU/plural/date data for
   free). *Cost of wrong:* an ICU edge case we did not implement; mitigated by parity
   tests, and swapping to Babel later is a contained change in `local_operator/i18n/`.
6. ⛳ **Docs/marketing/store-listings scope.** *Recommend:* out of scope v1 (§3.6);
   revisit after wave 1 ships. *Cost of wrong:* non-English users get translated product
   with English docs — acceptable, and cheaper than a second pipeline now.
7. **Envelope shape** (architect-level, recorded): `{code, params, text}` as in §2.6.
8. **Wave order** (architect-level): es+fr first, ur last.
9. **Digits** (architect-level, reversible): Latin digits for `hi`/`ur` in v1; per-locale
   style-guide reverts.
